# Foundation WebAssembly export and browser runtime

## Purpose and ownership

RustMultiConsoleFoundation defines a reusable Web/WASM publishing contract for games and engines that use the library. A consumer builds its own application module, then supplies its generated JavaScript glue, compiled WASM file and resource files to Foundation's export builder. Foundation validates the package description, stages a deployable directory and writes `web-export.json`. Its browser runtime consumes that same manifest to fetch and decode resources.

Ownership is deliberately split:

- **ImpossibleEngine:** editable `project.ieproj` projects, editor/source model, scenes, Event Sheets, objects, behaviors, scripts and source assets. Its publishing backend can use Foundation's export API.
- **RustMultiConsoleFoundation:** shared Web/WASM package contract, export builder and validation, directory staging, browser URL resolution, resource fetching/decoding, Canvas 2D and WebAudio host.
- **StreetChavesRust:** game simulation, game-specific resource identity/interpretation and a consumer-side export assembled through the Foundation API.

The format is generic. It does not encode another editor's project format or assume asset directory names. Every package path is explicit and relative to `web-export.json`.

## Package layout

A typical output directory looks like:

```text
web/
  index.html
  main.js
  web-export.json
  pkg/
    game.js
    game_bg.wasm
  assets/
    images/
    audio/
      effects/
      music/
    data/
```

The consuming project's WASM build generates the JavaScript glue and module. The publisher gives their source paths and desired destination paths to Foundation. The game or engine similarly maps each source asset into its destination in the package. Directory names and filename case are preserved.

Example manifest generated by the builder:

```json
{
  "schema_version": 1,
  "application": {
    "id": "street-chaves",
    "name": "Street Chaves"
  },
  "wasm": {
    "javascript_glue": "pkg/street_chaves.js",
    "wasm_module": "pkg/street_chaves_bg.wasm"
  },
  "assets": [
    {
      "id": "stage_01",
      "path": "assets/images/stages/stage-01.webp",
      "kind": "image"
    },
    {
      "id": "fight_hit_01",
      "path": "assets/audio/effects/hit-01.ogg",
      "fallbacks": [
        "assets/audio/effects/hit-01.m4a",

```

## Build an export with the Foundation library

The target-independent API is available from `foundation_runtime::web_export`. Native build/publishing tools can use it to copy the consumer's generated bundle and selected assets to the output directory:

```rust
use foundation_runtime::web_export::{
    WebAssetKind, WebExportAsset, WebExportBuilder,
};

let export = WebExportBuilder::new("street-chaves", "Street Chaves")
    .wasm_bundle_files(
        "target/web/street_chaves.js",
        "target/web/street_chaves_bg.wasm",
        "pkg/street_chaves.js",
        "pkg/street_chaves_bg.wasm",
    )
    .asset_file(
        WebExportAsset::new(
            "stage_01",
            "assets/images/stages/stage-01.webp",
            WebAssetKind::Image,
        ),
        "verified-assets/stage-01.webp",
    )
    .asset_file(
        WebExportAsset::new(
            "fight_music",
            "assets/audio/music/theme.ogg",
            WebAssetKind::Audio,
        )
        .with_fallbacks([
            "assets/audio/music/theme.m4a",
            "assets/audio/music/theme.mp3",
        ]),
        "verified-assets/theme.ogg",
    )
    // Fallback paths are manifest entries too, so register their source files.
    .package_file("verified-assets/theme.m4a", "assets/audio/music/theme.m4a")
    .package_file("verified-assets/theme.mp3", "assets/audio/music/theme.mp3")
    .package_file("web-source/index.html", "index.html")
    .package_file("web-source/main.js", "main.js")
    .write_to("dist/web")?;
```

`wasm_bundle_files` registers the JavaScript/WASM source files and their published paths. `asset_file` registers the primary source file for a catalogued resource. For each alternate encoding declared in `fallbacks`, register its source separately with `package_file` using the exact fallback destination path. `package_file` also adds files such as the HTML shell or consumer-owned JavaScript entry point. Finally, `write_to` validates the complete package, copies registered files into their declared destinations and writes the root `web-export.json`.

The builder checks the schema version, application identity, unique asset IDs, safe relative paths, fallback paths, duplicate destinations, missing source registrations and the audio volume range. Paths that are absolute or attempt to escape the package directory are rejected.

This creates a deployable directory package. The consuming project still owns its WASM compilation and decides which assets to include. This slice does not yet provide ZIP/archive output, an HTML template generator, media transcoding, automatic content-addressed optimization or a publisher CLI.

## Browser host

The optional `web-canvas` feature provides a browser host for `wasm32-unknown-unknown`:

- `Canvas2dHost` implements `RuntimeHost`.
- `DrawCommand`, `TextureId`, `AudioRequest` and `AudioClipId` remain backend-neutral.
- HTML Canvas 2D draws the ordered commands produced by the game.
- WebAudio plays clips registered by stable Foundation IDs.
- Browser key events are normalized into two-player input snapshots.
- WebGL is intentionally deferred.

Build the browser host:

```sh
rustup target add wasm32-unknown-unknown
cargo check -p foundation-runtime --target wasm32-unknown-unknown --features web-canvas
```

SDL3 remains behind `native-sdl3` and is not compiled for `wasm32-unknown-unknown`. A consumer commonly builds its own WASM module using `wasm-pack build --target web`, then stages that generated output with Foundation.

## Load the published package

Create the host around an existing canvas element:

```rust
let config = RuntimeConfig {
    title: "Game".into(),
    width: 400,
    height: 300,
    pixel_art: true,
};
let mut host = Canvas2dHost::from_canvas_id("game-canvas", config)?;
let assets = host.load_web_export("./web-export.json").await?;
```

The loader reads the manifest, resolves all resource paths relative to its URL, fetches the resources and registers decoded textures/audio clips. Data files are returned unchanged as byte arrays for game-specific parsing.

The browser application owns its `requestAnimationFrame` loop and calls the host at the appropriate points. The game simulation must continue using its own fixed logical tick; display refresh rate must not become the simulation clock.

The embedding page may resize the backing store using `resize_backing_store(css_width, css_height, device_pixel_ratio)`. It should call this after viewport, fullscreen or device-pixel-ratio changes. The logical game size does not change.

## Resource loading and limitations

- **Images:** PNG/BMP bytes are decoded into Foundation RGBA textures.
- **Audio:** the current browser host uses `decodeAudioData()` and retains decoded WebAudio buffers. Codec support varies by browser; declare alternate encodings when needed.
- **Data:** files are returned unchanged as bytes.

Effects and music may be stored in separate directories as a package organization choice, but both currently use the same buffered audio registration path. Music streaming is not implemented. A streaming feature needs its own fetch/decode/playback lifecycle, not just a manifest label.

HTTP, CORS, manifest and decode errors are surfaced. Serve the export over HTTP(S), and configure suitable CORS headers for cross-origin assets.

The browser host currently uses Canvas 2D, not WebGL. Browser gamepad and pointer/touch mappings are separate capabilities and are not implemented by this first adapter. WebAudio delegates final mixing to the browser, so output is not claimed to be bit-identical to the native S16 PCM mixer.
