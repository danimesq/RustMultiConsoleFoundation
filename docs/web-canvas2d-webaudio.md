# Foundation WebAssembly export and browser runtime

## Purpose and ownership

RustMultiConsoleFoundation owns the Web/WASM build and publishing pipeline for games and engines that use the library. A consumer supplies its Rust crate, build features, browser bootstrap and source-asset catalog. Foundation compiles the consumer crate, generates JavaScript/WASM glue, creates the HTML shell, stages resources, writes `web-export.json` and produces the deployable directory plus an optional ZIP archive. Its browser runtime consumes that same manifest to fetch and decode resources.

Ownership is deliberately split:

- **ImpossibleEngine:** editable `project.ieproj` projects, editor/source model, scenes, Event Sheets, objects, behaviors, scripts and source assets. Its publishing backend can use Foundation's export API.
- **RustMultiConsoleFoundation:** shared Web/WASM package contract, export builder and validation, directory staging, browser URL resolution, resource fetching/decoding, Canvas 2D and WebAudio host.
- **StreetChavesRust:** game simulation, game-specific resource identity/interpretation and a consumer-side export assembled through the Foundation API.

The format is generic. It does not encode another editor's project format or assume asset directory names. Every package path is explicit and relative to `web-export.json`.

## Package layout

A typical output directory looks like:

```text
web/
  index.html
  main.js
  web-export.json
  pkg/
    game.js
    game_bg.wasm
  assets/
    images/
    audio/
      effects/
      music/
    data/
```

The Foundation build command compiles the consuming project's Rust crate and generates the JavaScript glue and WASM module. The game or engine gives Foundation the crate/package identity, features, bootstrap source and asset-source mappings. Foundation maps those source files into package destinations. Directory names and filename case are preserved.

Example manifest generated by the builder:

## Build an export with the Foundation library

The target-independent API is available from `foundation_runtime::web_export`. Native build/publishing tools can use it to copy the consumer's generated bundle and selected assets to the output directory:

```rust
use foundation_runtime::web_export::{
    WebAssetKind, WebExportAsset, WebExportBuilder,
};

let export = WebExportBuilder::new("street-chaves", "Street Chaves")
    .wasm_bundle_files(
        "target/web/street_chaves.js",
        "target/web/street_chaves_bg.wasm",
        "pkg/street_chaves.js",
        "pkg/street_chaves_bg.wasm",
    )
    .asset_file(
        WebExportAsset::new(
            "stage_01",
            "assets/images/stages/stage-01.webp",
            WebAssetKind::Image,
        ),
        "verified-assets/stage-01.webp",
    )
    .asset_file(
        WebExportAsset::new(
            "fight_music",
            "assets/audio/music/theme.ogg",
            WebAssetKind::Audio,
        )
        .with_fallbacks([
            "assets/audio/music/theme.m4a",
            "assets/audio/music/theme.mp3",
        ]),
        "verified-assets/theme.ogg",
    )
    // Fallback paths are manifest entries too, so register their source files.
    .package_file("verified-assets/theme.m4a", "assets/audio/music/theme.m4a")
    .package_file("verified-assets/theme.mp3", "assets/audio/music/theme.mp3")
    .package_file("web-source/index.html", "index.html")
    .package_file("web-source/main.js", "main.js")
    .write_to("dist/web")?;
```

`wasm_bundle_files` registers the JavaScript/WASM source files and their published paths. `asset_file` registers the primary source file for a catalogued resource. For each alternate encoding declared in `fallbacks`, register its source separately with `package_file` using the exact fallback destination path. `package_file` also adds files such as the HTML shell or consumer-owned JavaScript entry point. Finally, `write_to` validates the complete package, copies registered files into their declared destinations and writes the root `web-export.json`.

The builder checks the schema version, application identity, unique asset IDs, safe relative paths, fallback paths, duplicate destinations, missing source registrations and the audio volume range. Paths that are absolute or attempt to escape the package directory are rejected.

This is the low-level package-staging API for build integrations that already have compiled browser artifacts. The standard source-driven workflow is `foundation_packaging::web_build::build_web_from_file()`, which performs the Cargo build, bindgen step, HTML generation, asset staging and ZIP creation inside Foundation.

## Foundation-owned source-to-WebAssembly build

RustMultiConsoleFoundation owns the Web build pipeline. Game and engine repositories provide their Rust source crate, build features, an optional browser bootstrap module, and a source-asset catalog. They do **not** compile WASM or assemble the final package themselves.

The Foundation packaging crate exposes:

- `foundation_packaging::web_build::WebBuildConfig`
- `foundation_packaging::web_build::build_web_from_file()`
- `foundation-web-build`, the CLI entry point

The builder invokes Cargo to compile the selected consumer package for `wasm32-unknown-unknown`, invokes `wasm-bindgen` to produce the JavaScript glue and WebAssembly module, generates an HTML shell, stages the compiled bundle and source assets through the shared `WebExportBuilder`, writes `web-export.json`, and creates a ZIP archive when configured.

Install the target and the matching wasm-bindgen CLI once on the build machine:

```sh
rustup target add wasm32-unknown-unknown
cargo install wasm-bindgen-cli
```

Example `FoundationWebBuild.toml`:

```toml
schema-version = 1
assets-root = "../OpenStreetChaves"

[application]
id = "street-chaves"
name = "Street Chaves"

[build]
project-dir = "."
manifest-path = "Cargo.toml"
package = "street-chaves-rust"
crate-name = "street_chaves"
features = ["web-foundation"]
target = "wasm32-unknown-unknown"
profile = "release"

[web]
title = "Street Chaves"
canvas-id = "street-chaves"
audio-button-id = "enable-audio"
diagnostics-id = "diagnostics"
bootstrap = "web/main.js"

[output]
directory = "dist/street-chaves-web"
archive = "dist/street-chaves-web.zip"

[[assets]]
id = "stage_01"
source = "Cenarios/Cenario-01.bmp"
path = "assets/images/stages/Cenario-01.bmp"
kind = "image"
source-url = "https://github.com/danimesq/OpenStreetChaves/blob/main/Cenarios/Cenario-01.bmp"

[[assets]]
id = "fighter_01"
source = "Lutadores/C01.bmp"
path = "assets/images/fighters/C01.bmp"
kind = "image"
source-url = "https://github.com/danimesq/OpenStreetChaves/blob/main/Lutadores/C01.bmp"

[[assets]]
id = "fighter_ini_01"
source = "Dados/Lutadores/C01.ini"
path = "assets/data/C01.ini"
kind = "data"
source-url = "https://github.com/danimesq/OpenStreetChaves/blob/main/Dados/Lutadores/C01.ini"
```

Build from the consumer repository:

```sh
cargo run -p foundation-packaging --bin foundation-web-build -- \
  --config FoundationWebBuild.toml
```

The result is a deployable directory and ZIP archive. Foundation generates the HTML shell using the configured canvas ID and optional audio-activation/diagnostics element IDs, then loads the consumer bootstrap as `main.js`. These optional controls let a bootstrap such as StreetChaves' bind its audio resume button and report runtime diagnostics without supplying a consumer-owned HTML page. When no bootstrap is configured, Foundation emits a minimal module that initializes the wasm-bindgen output.

The build configuration separates **source location** from **published location**. Source files are resolved under `assets-root`; published paths are package-relative and validated by Foundation. Optional `source-url` entries are retained in `web-build-provenance.json`, so packaged assets can keep direct links to their upstream files.

All build-time asset inputs must exist before compilation. Missing assets, unsafe paths, duplicate IDs, missing Cargo artifacts, missing wasm-bindgen output and tool failures stop the build with a diagnostic. The build never overwrites canonical source assets with target conversions.

### Build pipeline ownership

Foundation owns each stage:

1. Rust compilation for the selected target and profile.
2. Bindgen/glue generation for browser loading.
3. HTML shell generation and consumer bootstrap integration.
4. Source asset ingestion, path validation and package staging.
5. Target-specific image/audio conversion and optimization as build profiles add those processors.
6. Versioned package manifest and provenance output.
7. Directory and archive generation.
8. Artifact checksums, reproducibility metadata and final validation.

The current source-driven implementation completes stages 1–4 and 6–7 for the browser target. It copies source assets unchanged for now; codec transcoding, image optimization, generated alternate formats and streamed-music delivery are subsequent Foundation-owned build/runtime capabilities, not responsibilities delegated to StreetChavesRust or ImpossibleEngine.

ImpossibleEngine will call the same library API from its publishing backend once that backend is wired. StreetChavesRust remains an independent game project and uses Foundation directly; it does not depend on ImpossibleEngine.

## Browser host

The optional `web-canvas` feature provides a browser host for `wasm32-unknown-unknown`:

- `Canvas2dHost` implements `RuntimeHost`.
- `DrawCommand`, `TextureId`, `AudioRequest` and `AudioClipId` remain backend-neutral.
- HTML Canvas 2D draws the ordered commands produced by the game.
- WebAudio plays clips registered by stable Foundation IDs.
- Browser key events are normalized into two-player input snapshots.
- WebGL is intentionally deferred.

Build the browser host:

```sh
rustup target add wasm32-unknown-unknown
cargo check -p foundation-runtime --target wasm32-unknown-unknown --features web-canvas
```

SDL3 remains behind `native-sdl3` and is not compiled for `wasm32-unknown-unknown`. A standard consumer uses `foundation-web-build` to ask Foundation to compile its Rust crate and publish the resulting package. Direct `wasm-pack` builds remain useful for manual diagnostics, not the normal Foundation publishing path.

## Load the published package

Create the host around an existing canvas element:

```rust
let config = RuntimeConfig {
    title: "Game".into(),
    width: 400,
    height: 300,
    pixel_art: true,
};
let mut host = Canvas2dHost::from_canvas_id("game-canvas", config)?;
let assets = host.load_web_export("./web-export.json").await?;
```

The loader reads the manifest, resolves all resource paths relative to its URL, fetches the resources and registers decoded textures/audio clips. Data files are returned unchanged as byte arrays for game-specific parsing.

The browser application owns its `requestAnimationFrame` loop and calls the host at the appropriate points. The game simulation must continue using its own fixed logical tick; display refresh rate must not become the simulation clock.

The embedding page may resize the backing store using `resize_backing_store(css_width, css_height, device_pixel_ratio)`. It should call this after viewport, fullscreen or device-pixel-ratio changes. The logical game size does not change.

## Resource loading and limitations

- **Images:** PNG/BMP bytes are decoded into Foundation RGBA textures.
- **Audio:** the current browser host uses `decodeAudioData()` and retains decoded WebAudio buffers. Codec support varies by browser; declare alternate encodings when needed.
- **Data:** files are returned unchanged as bytes.

Effects and music may be stored in separate directories as a package organization choice, but both currently use the same buffered audio registration path. Music streaming is not implemented. A streaming feature needs its own fetch/decode/playback lifecycle, not just a manifest label.

HTTP, CORS, manifest and decode errors are surfaced. Serve the export over HTTP(S), and configure suitable CORS headers for cross-origin assets.

The browser host currently uses Canvas 2D, not WebGL. Browser gamepad and pointer/touch mappings are separate capabilities and are not implemented by this first adapter. WebAudio delegates final mixing to the browser, so output is not claimed to be bit-identical to the native S16 PCM mixer.
